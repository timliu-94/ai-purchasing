# 农产品收购管理 App V1.0 产品需求文档

## 一、产品概述

### 1.1 产品名称

暂定：农产品收购管理 App

英文名称及正式品牌名称后续确定。

### 1.2 产品定位

面向非洲小型咖啡豆、可可豆收购商的移动端收购记录工具。

第一版聚焦一个核心场景：

> **老板现场向农民收购咖啡豆或可可豆时，通过手机完成农民识别、农产品信息记录、拍照、称重、质量指标登记、农民签字及交易确认。**

系统替代目前可能使用的纸质记录、WhatsApp 图片、Excel 或人工记账方式，使每一次收购形成结构化、可追溯的电子记录。

### 1.3 第一版目标

第一版不追求建设完整 ERP，重点验证以下三个问题：

1. 老板是否愿意在每次收购时使用 App 进行记录；
2. App 是否能够完整替代纸质收购单；
3. 农民历史资料和收购记录是否能给老板带来实际管理价值。

如果这三个问题得到验证，再逐步扩展库存、付款、员工、工单、运输和出口管理等能力。

# 二、目标用户

## 2.1 老板

V1.0 中唯一需要登录系统的业务用户。

当前实际业务中，老板同时承担：

- 收购人员；
- 农民关系维护；
- 质量记录；
- 交易记录；
- 数据管理。

因此第一版不设置复杂的员工和角色体系。

系统后台仍然需要保留：

- User；
- Role；
- Permission；

等基础数据结构，为未来增加员工账号做好准备。

V1.0 默认角色：

**Owner / 老板**

拥有全部数据的查看、创建和修改权限。

---

## 2.2 农民

农民不需要注册账号，也不需要安装 App。

农民在系统中属于业务对象。

主要参与两个环节：

1. 建立农民档案；
2. 在完成农产品收购后进行签字确认。

农民签字完成后，可以直接对手机上的交易概要页面进行拍照留存。

后续版本可以增加：

- WhatsApp 发送凭证；
- 短信发送凭证；
- PDF 电子收购单；
- 农民独立账户。

# 五、核心业务流程

V1.0 整个业务流程尽量控制在一条主链路内。

## 5.1 标准收购流程

老板打开 App

↓

登录

↓

点击「新建收购」

↓

搜索农民

↓

选择已有农民 / 新建农民

↓

选择农产品

↓

录入重量

↓

录入质量指标

↓

拍摄农产品照片

↓

填写日期和备注

↓

确认收购信息

↓

农民签字

↓

生成交易概要

↓

向农民展示交易概要

↓

农民使用自己的手机拍照留存

↓

完成收购

整个流程原则上控制在 **2—3 分钟以内**。

# 九、质量指标

这一部分建议做成配置化，这是第一版扩展性最值得提前设计的地方之一。

不能直接在 App 中写死：

- 水分；
- 杂质；
- 发酵率。

因为咖啡豆和可可豆使用的指标不同，未来不同客户也可能使用不同指标。

建议采用：

**Product → Quality Indicator**

配置模型。

# 十七、签字后的数据修改规则

农民签字意味着交易信息已经得到确认。

因此签字后的记录不应该允许随意修改。

V1.0 建议：

### 签字前

老板可以自由修改。

### 签字后

核心字段锁定。

例如：

- Farmer；
- Product；
- Weight；
- Date；
- Quality；
- Signature。

如果确实录入错误，老板可以：

**Void / 作废**

原记录。

然后重新创建一笔收购。

系统保留被作废的原始记录。

这样比第一版制作复杂的“修改审批流程”更简单，同时又保证数据可靠性。

农民。

---

## Product

农产品。

---

质量指标定义。

---

## Purchase

收购主记录。

核心关系：

**Purchase → Farmer**

**Purchase → Product**

## Purchase Quality Value

某次收购实际填写的质量指标值。

例如：

```text
Purchase = PUR001
Indicator = Moisture
Value = 7.5
```

这样避免在 Purchase 表中直接增加：

```text
moisture
fermentation
defect_rate
...
```

这是保证未来扩展性的一个关键设计。

---

## Purchase Image

收购图片。

---

## Signature

农民签名。

# 二十二、建议的数据关系

整体关系可以理解为：

```text
Farmer
   │
   │ 1:N
   ▼
Purchase
   │
   ├──── Product
   │
   ├──── Purchase Quality Value
   │          │
   │          └──── Quality Indicator
   │
   ├──── Purchase Image
   │
   └──── Signature
```

这一模型足够支撑第一版，同时未来可以继续向 Purchase 后增加：

```text
Payment
Inventory
Warehouse
Employee
Work Order
Export Batch
```

因此第一版虽然产品功能很轻，但底层数据模型没有把后续扩展堵死。

# 二十四、接口设计原则

Android 和 Web 不直接访问数据库。

统一通过 Backend API 操作。

例如：

```text
POST /api/login

GET /api/farmers

POST /api/farmers

GET /api/farmers/{id}

POST /api/purchases

GET /api/purchases

GET /api/purchases/{id}

POST /api/purchases/{id}/images

POST /api/purchases/{id}/signature

POST /api/purchases/{id}/confirm
```

这样未来无论增加：

- iOS；
- 员工 App；
- 农民 App；
- 第三方系统；

都可以复用相同的后端服务。

# 二十五、网络要求

第一版建议先采用：

**在线模式为主。**

即：

有网络时正常创建和上传收购记录。

但开发过程中应避免把业务逻辑设计成完全依赖实时网络。

Android 本地需要至少能够：

- 暂存填写中的表单；
- 防止 App 意外关闭导致数据丢失；
- 图片先保存在本地；
- 上传失败后重新上传。

完整的：

**Offline First / 离线同步**

可以作为 V1.1 的重点能力。

因为离线同步涉及：

- 本地数据库；
- 数据冲突；
- 图片任务队列；
- 重复记录；
- 状态机；

会显著增加第一版开发复杂度。

第一版可以先通过实际用户测试，判断弱网究竟是否构成核心问题。

# 二十九、第一版成功指标

V1.0 最重要的指标不是 DAU 或复杂经营指标，而是验证产品是否能够进入真实交易过程。

建议重点观察：

### 收购电子化率

实际发生的收购中：

多少比例通过 App 完成记录。

目标：

**>80%**

### 收购完成率

开始创建的收购单中：

多少成功完成农民签字。

目标：

**>95%**

### 单次录入时间

从点击：

**New Purchase**

到农民完成签字。

目标：

**<3 分钟**

### 农民复用率

已有农民再次交易时：

是否能够直接找到原有档案，而不是重复创建。

### 用户反馈

老板是否认为：

> App 比纸质记录更加方便。

这是第一版最关键的验证结果。
